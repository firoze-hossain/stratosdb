# StratosDB — Project Plan

This merges the planning documents that existed for this project and reconciles them against what's actually true of the codebase today:

1. **The 4-week foundation roadmap** — written after actually auditing the repo, scoped to what a single developer (plus AI-assisted pair programming) can realistically build and verify in a month. Now complete — see Part 1.
2. **The "DeepSeek" project plan** — a much broader, longer-horizon feature catalog (18 months, a 6-person team, an $842K budget) aimed at eventual feature parity with PostgreSQL.

Both are useful for different things. Document 2's feature enumeration (MVCC, JOINs, indexing, wire protocol, replication, extensibility...) is a genuinely reasonable map of *what a serious relational database needs*, and it's kept below, reorganized as the long-term vision. Its team size, budget, and month-by-month dates are not adopted — they describe a fully-staffed commercial effort, not what's actually happening here, and repeating them would just be decoration. Its "current status" claims (10,000+ lines, MVCC done, various things "✅ COMPLETED") were also not adopted where they didn't match the real repo — see `PROGRESS.md` for what's actually verified.

Part 2 was extended to directly address the actual goal behind both source documents: building something as professional as PostgreSQL, or better than it. That phrase is treated with the same honesty standard as everything else here — see "Read this before the task list," below, for what it does and doesn't mean.

**For live, checkmarked status, see `PROGRESS.md`. This document is the map; that one is the odometer.**

## Part 1: The Foundation (weeks, not months — complete)

Goal, stated once so every later phase can be measured against it:

> A single-node relational engine that is **correct under crash and concurrency**, supports real SQL (joins, indexes, transactions with isolation), and is reachable over the network from a JDBC client — with tests and benchmarks proving the claims, not just asserting them.

### Week 1 — Storage durability ✅
Real WAL redo, real crash-recovery testing (kill a forked JVM mid-batch, restart, verify), fixed buffer-pool/heap-table bugs that caused silent data loss. Done — see PROGRESS.md.

### Week 2 — Transactions that actually isolate ✅
MVCC with snapshot isolation (xmin/xmax, Postgres-style visibility rules), a lock manager with deadlock detection, `UPDATE`/`DELETE` actually implemented (they were no-op stubs). Done — see PROGRESS.md.

### Week 3 — SQL engine and indexing ✅ complete
- B+Tree index: **done** — disk-backed, real node splitting, tested at 250k-key scale.
- `CREATE INDEX` + index-scan-vs-seq-scan planner choice in the executor: **done** — see PROGRESS.md.
- `EXPLAIN`-style output: **done** — including a description of the join shape for joined queries.
- JOIN support (nested loop minimum): **done** — see PROGRESS.md for the test coverage and known limitations (no index-accelerated joins yet).
- Benchmark (indexed point lookup vs. full scan, 100k+ rows): **done** — 97.5x speedup measured for real, see PROGRESS.md.

### Week 4 — Reachable, secure, provable ✅ complete
- Wire protocol + socket server: **done** — `stratosdb-network`, virtual-thread-per-connection, tested over real sockets.
- Minimal JDBC driver: **done** — `stratosdb-jdbc`, verified through `java.sql.DriverManager`. See PROGRESS.md for what's real vs. stubbed (dynamic-proxy fallback throws `SQLFeatureNotSupportedException` for the large parts of `Connection`/`Statement`/`ResultSet` not implemented).
- CLI shell talking over that protocol: **done** — verified end-to-end against a real, separate server process.
- Auth: **done** — real PBKDF2 salted password hashing, a mandatory handshake on every connection.
- TLS: **done** on the server side (a real certificate-backed `SSLContext`); client-side certificate verification is honestly not implemented yet (trust-all only) - see PROGRESS.md for exactly what that does and doesn't protect against.
- Real throughput/latency benchmark numbers: **done** in Week 3 (97.5x indexed speedup, measured).

**All four weeks of the Foundation are complete.** Explicitly out of scope for this phase, and why that's fine: cost-based query optimization, replication, full vacuum/autovacuum, extensions, stored procedures, triggers, partitioning, client-side TLS certificate verification. Each of these is itself a multi-month-to-multi-year undertaking in Postgres's own history (or, for client TLS verification, a genuinely important but separable next increment). A month-one engine is the correct base to eventually build them on, not a substitute for them.

## Part 2: Toward professional-grade — what matching, and in specific places exceeding, PostgreSQL actually requires

### Read this before the task list

PostgreSQL is the product of roughly 30 years and thousands of contributors, with a massive surrounding ecosystem (extensions, hosting providers, tooling, and decades of production battle-testing across nearly every workload imaginable). Matching it feature-for-feature is not something a solo-developer-plus-AI effort should claim a timeline for — that's a difference in *kind* of effort, not just amount, and no roadmap changes that fact. Saying so plainly here is the same standard this plan has held to since Part 1: real claims, backed by what's actually true, not aspirational framing.

"Better than PostgreSQL" is not one claim — it's several, and they don't all move together. Here's where a from-scratch, modern, pure-Java engine could plausibly have a *real, durable* edge, assessed honestly:

- **Embeddability.** PostgreSQL requires a separate server process, always. StratosDB already runs in-process as a library (Part 1's whole embeddable-core design). For embedded, edge, or test-fixture use cases, this is a structural advantage that doesn't erode over time — Postgres would have to be redesigned to remove it.
- **Zero native dependencies.** Pure JVM bytecode, no `libpq`, no platform-specific builds, runs anywhere a JVM runs. Also durable.
- **A smaller, more legible codebase.** Real LOC counts are in `PROGRESS.md` — StratosDB's entire engine is a few thousand lines; Postgres's is well over a million. Easier to read, audit, and modify for a specific purpose. Genuinely valuable for teaching, research, or forking into a specialized variant. **Not** an advantage for raw performance, feature breadth, or robustness under load — those favor decades of tuning, not a smaller codebase.

And where StratosDB is honestly not going to be "better" any time soon, stated as plainly as the rest of this plan: query optimizer sophistication (decades of tuning against real workloads), the extension ecosystem (PostGIS, `pg_vector`, hundreds of others), replication and HA maturity, raw throughput at scale, and — perhaps most importantly — the sheer volume of production battle-testing that surfaces edge cases no test suite invents on its own.

Given that, the real goal for Part 2 is: close the feature gaps that matter most for actual usage, in priority order, each backed by a real test — the exact standard Part 1 was held to throughout. "Better than PostgreSQL" is realistically an aspiration for a narrow, specific set of properties (embeddability, portability, code legibility), not a blanket claim, and everything below is honest about that split.

### Priority framework

There's no team to divide across streams, so priority replaces scheduling — what to build next, based on (a) how much real usage it unlocks per unit of effort, and (b) what it's a prerequisite for. No calendar dates, for the same reason Part 1 never used them: a solo/AI-paced date for work this size would be fiction the moment it was written.

- 🔴 **Critical** — blocks real usage, or blocks several later items.
- 🟡 **High** — meaningfully expands what the engine can actually do today.
- 🟢 **Medium** — valuable, not urgent.
- ⚪ **Long-horizon** — genuinely multi-year even for a funded team; named for honesty, not committed to.

### Phase A — Harden and complete the storage layer 🔴

| Task | Priority | Depends on | Notes |
|---|---|---|---|
| Persisted commit-status log + persisted xid counter | ✅ done | none | Found while testing savepoints' crash-safety: `TransactionManager`'s "which xids committed" tracking was in-memory only and reset on every restart, and xids themselves restarted from 1 every session - so a row's visibility after *any* restart (not just a crash) could depend on incidental transaction-id coincidence rather than being reliably correct. Fixed with a batch-reserved persisted xid counter (never reused across any number of restarts) and an append-only, `fsync`'d commit log read back on startup. Verified adversarially: a table with a single `CREATE TABLE` (minimal catalog replay) plus 20 inserts (transaction ids running far ahead of replay) correctly survives four sequential real restarts with mixed insert/update/delete, checked via exact row counts and values. See PROGRESS.md. |
| Schema catalog persistence | ✅ done | none | `CREATE TABLE`/`CREATE INDEX`/`CREATE VIEW` were purely in-memory - a table's heap file survived a restart correctly (that was fixed in Week 1) but the engine had no record the table existed at all, so a restart reported "table not found" for data sitting right there on disk. Fixed with a catalog file that replays table/view DDL as SQL text and reconstructs indexes structurally (avoiding a rescan that would duplicate an already-populated index file). See PROGRESS.md. |
| Sequences, `SERIAL`/`BIGSERIAL`, auto-increment | ✅ done | none | `CREATE SEQUENCE`/`DROP SEQUENCE`, `nextval()`/`currval()` (correctly per-session, matching real Postgres), `SERIAL` as sugar auto-creating a backing sequence wired as a column's default. Building this surfaced two real, severe, pre-existing bugs found and fixed along the way, neither specific to sequences: INSERT's explicit column list was silently discarded (values mapped positionally against the full schema instead of the named columns), and a genuine concurrent-insert data-loss race in `HeapTable.insert()` (see the storage engine row above and PROGRESS.md for the full diagnosis). |
| WAL redo idempotency across restarts | ✅ done | none | `checkpoint()` wrote a marker but never cleared the log, and `recover()` always replayed from byte zero with no notion of "already applied" - so even the first restart after a clean shutdown duplicated every already-durable row, and every further restart would have duplicated again. Fixed by truncating the log (safely - every redone write is individually fsynced first) after both `recover()`'s redo pass and a graceful `close()`. Verified across three sequential restarts, not just one. See PROGRESS.md. |

| Vacuum | ✅ done | none | Real reclamation (mark-then-compact via SlottedPage.defragment, previously a stub), gated on TransactionManager.getOldestActiveXid so an active older transaction's snapshot is never broken - proven directly with real, separately-controlled transactions, not simulated. Autovacuum (Phase E) is now done too, automating this. |

Vacuum reclaiming dead tuples doesn't produce this by itself - it's a separate structure to build. |
| Free-space map | 🟡 | none | `HeapTable.insert()` currently scans every existing page looking for room — O(pages) per insert. A free-space map makes this O(1) amortized. |
| Real prepared statements (wire-level) | 🟡 | none | `StratosConnection.prepareStatement()` currently throws `SQLFeatureNotSupportedException`. Needs an actual `PARSE`/`BIND`/`EXECUTE` split in the JDBC driver's own native protocol (`com.stratosdb.network.protocol.WireProtocol`) — not client-side string substitution, which would just move the SQL-injection-shaped risk around rather than removing it. The two protocols don't share an implementation, so finishing one didn't finish the other. |

### Phase B — Query engine depth 🔴

The largest single gap versus PostgreSQL, and the highest-leverage phase for "feels like a real database" rather than "a working prototype."

| Task | Priority | Depends on | Notes |
|---|---|---|---|
| Statistics collection (`ANALYZE`-equivalent) | ✅ done | none | Row counts and per-column distinct-value/min/max estimates - see PROGRESS.md. In-memory only, no auto-refresh on writes (that's autovacuum's job, Phase E) - can go stale exactly like Postgres's own statistics without a periodic ANALYZE. |
| Cost-based optimizer | ✅ done | Statistics | Replaced the rule-based planner with real cost comparison (seq scan vs. index scan), falling back to the old rule-based heuristic when no statistics exist. Demonstrated with real data switching plans correctly in both directions - see PROGRESS.md. Known limitation: assumes uniform value distribution (no histogram/MCV tracking like real Postgres), and doesn't yet inform join-strategy choice (hash join is still unconditional, not compared against alternatives). |
| `GROUP BY` / `HAVING` / aggregates (`SUM`/`COUNT`/`AVG`/`MIN`/`MAX`) | ✅ done | none | Was completely absent, now real - see PROGRESS.md. Known gap: doesn't combine with JOIN yet (a query using both silently skips grouping rather than erroring - a named follow-up). |
| Hash join | ✅ done | none | Replaced nested-loop as the sole join algorithm - see PROGRESS.md for real measured numbers (4.4x-10.9x, widening with scale, exactly as O(n·m) vs O(n+m) predicts). Not yet a genuine cost-based *choice* between strategies (there's still no statistics to base one on) - it's "always hash join," which is correct since every JOIN this grammar supports is equality-only. |
| Subqueries (scalar, `EXISTS`, `IN`) | ✅ done | none | Scalar comparison, `IN`/`NOT IN`, `EXISTS`/`NOT EXISTS` including correlated `EXISTS` - see PROGRESS.md. Built on top of a real WHERE-clause expression tree that replaced the previous raw-text design (which had silently broken `AND`/`OR`/`NOT`/`LIKE`/`IN` - a real bug found and fixed along the way, not a hypothetical one). Known limit: correlation isn't threaded through a subquery that itself contains a JOIN or GROUP BY. |
| Merge join | ✅ done | none | A real second join strategy alongside hash join, chosen by a simple, honest row-count threshold (both sides above 10,000 rows) rather than a full cost model - hash join's whole build side has to fit as one in-memory hash table, a real cost once both sides are large; merge join sorts both sides instead (no single huge structure). Verified algorithmically identical to hash join on input with duplicate and NULL join keys, and that the planner's threshold actually routes large joins to it - see PROGRESS.md. |
| Window functions | ✅ done | Aggregates | `ROW_NUMBER`/`RANK`/`DENSE_RANK` with `PARTITION BY`/`ORDER BY`, verified against real Postgres semantics (partitioning, real tie-handling for RANK vs DENSE_RANK, JOIN/aggregate rejection, empty tables). |
| CTEs, `WITH RECURSIVE` | ✅ done | none | Non-recursive: reuses views' own execution path almost entirely - a CTE is "a view scoped to one statement," inheriting views' JOIN/aggregate rejection for free, with a real concurrency risk (shared-state CTE storage racing under concurrent connections) identified and designed around before it became a bug. Recursive: real fixpoint iteration (base case seeds the result; the recursive branch repeatedly runs against only the previous iteration's new rows - real Postgres "working table" semantics - until nothing new is produced or a 1000-iteration safety cap is hit). A real design flaw was caught before shipping (the standard hierarchy/graph-traversal pattern needs the CTE to work as a JOIN target, not just a bare FROM, requiring join-source resolution to be extended) and a real bug was found by actually testing a 6-person hierarchy (a recursive branch's own qualified column names silently broke the next iteration's join - fixed by aligning every iteration's columns to the base query's schema positionally, matching how UNION ALL actually matches columns). Known gap: no cycle detection beyond the iteration cap. |

### Phase C — More indexing 🟡

| Task | Priority | Depends on | Notes |
|---|---|---|---|
| Hash index | ✅ done | none | Real disk-backed static hashing with overflow chaining, built on the same Page/BufferPool infrastructure as BTreeIndex (reuses BTreePage's leaf layout as the bucket format). A shared `KeyValueIndex` interface lets the planner treat it and BTreeIndex uniformly for equality lookups, preferring hash when both exist on a column. Verified at 100k-key scale forcing real overflow chains - see PROGRESS.md. Known limitation: static bucket count, no dynamic splitting as the index grows. |
| Index-only scans | ✅ done, scoped to equality | none | Needed to confirm a tuple is visible without touching the heap at all - built a real visibility map for exactly this (a per-page bit meaning "every tuple here has a committed xmin and no xmax at all," set by vacuum, cleared by insert/update/delete). Used for an equality query whose WHERE clause is exactly that one comparison and whose projection asks for only the indexed column - when the page is confirmed all-visible, the index's own key is trusted directly, skipping the heap fetch. Two real bugs were found by testing before this was correct: a type mismatch (Long vs Integer for the same INT column depending on which path ran) and, while fixing that, a classic Java ternary-operator numeric-promotion gotcha (JLS 15.25) that silently undid the first fix - see PROGRESS.md. Known, named gap: range scans aren't covered yet, since `BTreeIndex.rangeScan()` currently returns bare row identifiers, not key-identifier pairs, so there's no per-row key to trust without fetching the heap anyway. |
| BRIN | ✅ done | none | Real block-range (min, max) summaries rather than one entry per row - cheap to build/maintain, lossy by design (rules ranges OUT, never confirms a match), ideal for a column correlated with physical insertion order. Actually used during a scan (`tryBrinIndexScan`), not just built: narrows which pages are worth reading at all, then does a real, restricted scan of just those - verified with 200 rows across multiple page ranges. |
| Bitmap index | ✅ done | none | Real per-distinct-value `BitSet`s (not a relabeled B+Tree), for low-cardinality columns. Used during a scan only when no faster BTREE/HASH already covers the column. Bitwise AND/OR combination across multiple conditions exists (`searchCombined`) but isn't yet wired into a multi-condition WHERE clause - a further step, not attempted here. |
| GIN | ✅ done - text search, arrays, and JSON, all three | none | Real Postgres's GIN is a genuinely general framework (arrays, JSONB, full-text, via pluggable operator classes). Implemented as three of its most common real applications: a genuine inverted index for whole-word text search (`CONTAINS`, works correctly with no index at all - same relationship `LIKE` has with indexes); real array-element indexing (`insertExact`, distinct from text search's tokenizer - array elements need exact matching, e.g. `"low-priority"` must stay one value, not get tokenized into two) powering `@>` containment; and real JSON key-value indexing (each top-level key-value pair indexed as a composite `"key:value"` exact key) powering `->>'key' = 'value'`. Known gaps: text search is whole-word matching only, no stemming/stop-words/ranking; `@>` compares against a single scalar element, not full array-to-array containment; `->>` reaches only top-level JSON keys with equality only, no nested paths. |
| GiST | ✅ done, scoped to interval overlap | none | Real GiST is a framework for indexing arbitrary "consistent" predicates (classically: geometric overlap, range containment) via a balanced tree of predicates that generalize over their subtrees - not just another way to compare a single scalar value, which is all B+Tree/hash/BRIN/bitmap/GIN already cover well. Implemented as GiST's own classic real-world application: interval-overlap over a `(start, end)` column pair (`(start, end) OVERLAPS (queryStart, queryEnd)`), needing real multi-column index support first (`CREATE INDEX ... (col1, col2) USING GIST`), which didn't exist at all before this and still correctly stays GIST-only - every other index type still rejects a second column. `GistIntervalIndex` is a real tree with real bounding-interval predicates at internal nodes and real pruning during search - verified correct at scale (200 entries, 30 random query trials) against an independent brute-force oracle, not hand-computed expected values. Known, honestly-stated simplification: the tree is rebuilt from all entries on every insert rather than incrementally inserted-and-split the way a real R-tree would (O(n log n) insert instead of O(log n)) - search's pruning correctness is not simplified. |


### Phase D — Networking, protocol compatibility, and real transactions 🟡

| Task | Priority | Depends on | Notes |
|---|---|---|---|
| Multi-statement transactions over the wire (`BEGIN`/`COMMIT`/`ROLLBACK` as real protocol operations) | ✅ done | none | `Connection.setAutoCommit(false)` no longer throws - real `BEGIN`/`COMMIT`/`ROLLBACK`, transaction poisoning on a failed statement (matching Postgres), and a real crash-recovery test proving atomicity via an actual `SIGKILL` mid-transaction. See PROGRESS.md - including an honest note that the SQL-engine core of this predated this round and was found already built but undocumented; this round verified it, fixed the JDBC driver never using it, and fixed a real gap where its crash test existed but was silently excluded from every test run. |
| PostgreSQL wire protocol compatibility | ✅ done (simple + extended query protocols, SCRAM-SHA-256, `\dt`) | none | The startup handshake, simple query protocol, the extended query protocol (real `Parse`/`Bind`/`Describe`/`Execute`/`Sync`/`Close` message handling, real server-side prepared-statement and portal lifecycle), and now real SCRAM-SHA-256 authentication (RFC 5802) - verified against real, unmodified `psql` and `psycopg2` (including `psycopg2`'s default parameterized-query API, which uses the extended protocol automatically, and its automatic SCRAM negotiation, which needs no special configuration), plus this project's own native `stdsql` client, not a simulation. `psql -h host -p port -U user db` now just works: CREATE/INSERT/SELECT/UPDATE/DELETE, formatted output, real transactions (including matching Postgres's own "transaction is aborted" recovery behavior), NULLs, CTEs, `\dt`, parameterized queries (`cur.execute("... WHERE id = %s", (1,))`), and now real password authentication (`psycopg2.connect(..., password="...")`, rejecting a wrong password with the same error message real Postgres gives) all confirmed. One real, honestly-stated simplification in the extended protocol: parameters are substituted as properly escaped SQL literals into the query text rather than through a native parameterized-execution path (this engine has no such concept, having no query-planning phase separate from running a statement) - a real implementation of the wire protocol's message handling and lifecycle, just not a reusable pre-planned query the way Postgres's own server-side prepared statements are; values remain correctly escaped, so this stays injection-safe. A real, previously-latent bug was found and fixed while building this: the SQL grammar's `STRING_LITERAL` token never supported the standard `''` quote-escaping convention at all - see PROGRESS.md. A second real bug was found by a direct audit of the extended protocol's own coverage afterward: a failed `Bind` didn't put the connection into Postgres's own "skip every message until the next `Sync`" error-recovery state, so a later message could silently pick up a stale, unrelated portal instead of correctly doing nothing - fixed, with the fix itself needing to distinguish a genuinely invalid statement/portal reference (a real protocol error) from an otherwise-valid Bind whose substituted query fails at execution (which must still let a later Execute report that failure, not have it silently swallowed) - see PROGRESS.md. SCRAM-SHA-256 reuses `UserStore`'s existing PBKDF2 hash directly (exactly what SCRAM itself calls `SaltedPassword`), rather than a second, parallel credential store, and was verified against an independent, from-scratch client-side SCRAM implementation sharing no code with the server (see PROGRESS.md) before ever touching a real client. Known, named gaps: SCRAM channel binding (the TLS-integrated `SCRAM-SHA-256-PLUS` variant - this handshake accepts a client's "no channel binding" header at face value, matching what real Postgres also offers by default over a non-channel-bound connection), and `\d TABLENAME`/`\l`/tab-completion (captured their real queries and confirmed materially more complex than `\dt` - `\d` needs a multi-query OID lookup chain, `\l` needs a "multiple databases" concept this engine doesn't have). **Independence, stated explicitly**: this is StratosDB's own original code implementing a published, open protocol *specification* - there is no PostgreSQL source code, jar, binary, or other dependency anywhere in this project (verified by grepping every `pom.xml` and `.java` file). `psql`/`psycopg2` were used only as external test tools to verify correctness, the same way a browser tests a web server without the server depending on the browser; neither is linked into the build or required at runtime. This is also why the feature is named `stdwire`/`--stdwire` rather than `pgwire`, and defaults to port `6582`/`6583` rather than Postgres's own `5432`/`5433` - the naming shouldn't imply a dependency that doesn't exist. |
| SCRAM-SHA-256 auth | ✅ done | none | A real RFC 5802 implementation (`ScramSha256`), not a simplified stand-in - reuses `UserStore`'s existing PBKDF2 hash directly (exactly what SCRAM itself calls `SaltedPassword`) rather than a second credential store. Verified against an independent, from-scratch client-side SCRAM implementation sharing no code with the server, then against real, unmodified `psql` and `psycopg2` (which negotiates it automatically, no special configuration needed) - see the wire protocol compatibility row above and PROGRESS.md for the full detail. Known gap: SCRAM channel binding (`SCRAM-SHA-256-PLUS`) isn't implemented, matching what real Postgres also offers by default over a non-channel-bound connection. |
| Client-side TLS certificate verification | 🟡 | none | Named as an explicit, current gap in `PROGRESS.md` — the JDBC driver trusts any server certificate today. A real truststore (or certificate pinning) closes this. |
| Streaming replication (leader → follower) | 🟡 | none — the WAL redo mechanism from Week 1 is most of the mechanical prerequisite already | Largely "ship the WAL bytes elsewhere and replay them"; the hard part is failure handling (follower catch-up, leader failover), not the core replay logic, which already exists and is tested. |
| Connection pooling | 🟢 | none | Standard, well-understood pattern; low technical risk, real value once more than one client is hitting the server. |
| Logical replication | ⚪ | Streaming replication | Meaningfully harder — needs to decode the WAL into logical row changes rather than replay physical pages, a different representation than what the WAL currently stores. |

### Phase E — Extensibility & operations 🟢

| Task | Priority | Depends on | Notes |
|---|---|---|---|
| Views | ✅ done | none | Non-materialized - a stored query, re-run fresh on every SELECT, with the outer query's WHERE/projection/LIMIT applied to its rows. See PROGRESS.md for two real bugs found and fixed while building this (a view combined with JOIN/aggregate silently ignoring the join/aggregate instead of erroring, and a subquery failure silently treated as "no match" instead of surfacing). Known limit: no joining a view against a table, no aggregating over a view, no view-inside-a-subquery yet - all fail cleanly rather than doing something wrong. |
| Metrics (JMX or Prometheus-style) | ✅ done (as a queryable SQL surface) | none | `SHOW STATS` exposes buffer pool hit ratio, buffer pool cache size, current WAL LSN, table/view/index counts, and oldest active transaction id as an ordinary query result. The numbers already existed (the CLI's own `\status` tracked some of them) but were reachable only from that one specific command - now any SQL client (`psql`, a monitoring script, a BI tool) can read them. Known, named gap: this is a flat key-value snapshot, not a proper `pg_stat_activity`/`pg_stat_user_tables`-shaped surface with per-table or per-connection breakdowns - real further work. |
| Autovacuum (automatic, background) | ✅ done | none | A background thread periodically calling VACUUM on every table, through the exact same statement-execution path a manual VACUUM would use - see PROGRESS.md for the real reasoning behind that choice (this project's storage engine doesn't have fine-grained page/table locking, so routing through the same path manual vacuum always used avoids introducing a *new* separately-reasoned-about concurrency risk, rather than solving concurrency control in general). Verified: a scheduled background pass reclaims automatically, and stopping it is proven to actually stop it. |
| Triggers | ✅ done | none | `CREATE TRIGGER name {BEFORE|AFTER} {INSERT|UPDATE|DELETE} ON table FOR EACH ROW EXECUTE {FUNCTION|PROCEDURE} handler()` / `DROP TRIGGER name ON table` - a real event model wired into all three write paths (INSERT/UPDATE/DELETE), each with both a BEFORE and an AFTER firing point, with the handler's own parameters bound to the affected row's columns by exact name match. Real, honestly-stated, deliberate differences from Postgres's own trigger model: EXECUTE PROCEDURE is allowed (not just EXECUTE FUNCTION, real Postgres's own requirement) since this engine's procedures - real side effects, no return value needed - are actually the more natural fit for a trigger's own purpose; a BEFORE trigger here cannot modify the affected row or cancel the operation the way real Postgres's own BEFORE triggers can, since this engine's functions/procedures have no return-value mechanism for that; CREATE TRIGGER itself validates the referenced handler exists up front, not deferred to first use. A failing trigger fails the whole triggering statement, matching real Postgres's own behavior, not a swallowed warning. A real, previously-latent transactional bug was found and fixed by testing this directly: a trigger's own effects used to commit independently of the statement that fired it (via the public execute(String), which always starts and separately commits its own transaction), so when two triggers fired on the same event and the second failed, the first trigger's already-committed effects survived even though the triggering row itself correctly rolled back - fixed by threading the real transaction through invokeFunction/runProcedure/fireTriggers, dispatching directly against it instead. This also gave CALL's own multi-statement bodies genuine atomicity with each other for the first time, closing what had been an explicitly documented limitation. Known, named gaps: trigger names are assumed globally unique (not scoped per-table the way real Postgres allows); triggers fire in no particular guaranteed order when more than one matches the same event (real Postgres orders them alphabetically by name); an UPDATE trigger only sees the row's new (post-assignment) values, with no separate OLD/NEW binding the way real Postgres has both; only FOR EACH ROW is implemented, not FOR EACH STATEMENT. |
| Slow-query logging | ✅ done | none | `ExecutorEngine.setSlowQueryThresholdMs` / `DatabaseConfig.setSlowQueryThresholdMs` - logs any statement at or over the threshold at WARN with its elapsed time and text. Off by default. Timing wraps the whole statement (parse + dispatch + commit/abort bookkeeping), not just inner execution. |
| Real, SQL-language stored functions | ✅ done | none | `CREATE [OR REPLACE] FUNCTION name(params) RETURNS type AS $$ body $$ LANGUAGE SQL` / `DROP FUNCTION` - real grammar (including a new `$$ ... $$` dollar-quoted body delimiter, Postgres's own convention), real catalog persistence (survives a real restart, verified), and real parameter substitution (word-boundary-aware, properly quoted/escaped - the same real approach and injection-safety property as the extended query protocol's own parameter binding). Function calls in a SELECT list accept live column-reference arguments, not just literals (`SELECT order_count(id) FROM customers`) - the difference between a genuinely useful scalar function and a decorative one. A real, previously-undiscovered limitation found by testing: this engine's own SELECT doesn't support a bare arithmetic expression as a select item at all, so a function body is constrained to what SELECT can already express (column projections, aggregates, WHERE clauses on real tables) - every example here queries a real table rather than computing on its own parameters, which is both honest about the constraint and the actually valuable use case anyway. Known, named gaps: `LANGUAGE SQL` only (no procedural language - no variables, loops, or conditionals), not yet combinable with a JOIN/aggregate/window function in the same SELECT. |
| Real, SQL-language stored procedures | ✅ done | Real, SQL-language stored functions (shares the same parameter-substitution mechanism and $$-delimited body syntax) | `CREATE [OR REPLACE] PROCEDURE name(params) AS $$ body $$ LANGUAGE SQL` / `DROP PROCEDURE` / `CALL name(args)` - unlike a function's single-SELECT-expression body, a procedure's body may hold *multiple* semicolon-separated statements, executed in order when CALLed (the real, distinguishing design decision here, not just the missing RETURNS clause) - a procedure's own purpose is running a sequence of side-effecting statements, not computing one scalar value. `CALL` stops at the first failing statement, identifying which one and its own text, rather than continuing or failing silently at the end. The same real, previously-discovered UPDATE-grammar limitation (no arithmetic on an existing column's value) resurfaced here too - every example uses literal-style SET assignments instead, both honest about the constraint and a realistic pattern (state transitions) procedures are actually used for. Verified with a full round trip over the real wire protocol, not just the in-process API, including its own correct command tags (`CREATE PROCEDURE`/`DROP PROCEDURE`/`CALL`) - closing the same "generic OK fallback" gap already found and fixed for functions/sequences, before it could recur here. Known, named gaps: `LANGUAGE SQL` only (no procedural language, no OUT/INOUT parameters); the body is split on a plain top-level `;` (a semicolon inside a string literal within the body isn't supported - would need a real SQL tokenizer, not a text split); no implicit transaction wraps a CALL's own statements (wrap the CALL itself in BEGIN/COMMIT for atomicity); a CALL argument must be a literal (no column-reference resolution, since CALL has no row context to resolve one against). |

### Phase F — Scaling ⚪ (genuinely long-horizon, named for honesty)

- **Parallel query execution, table partitioning**: real and valuable, each independently a multi-month undertaking even with the cost-based optimizer (Phase B) already in place, since both need the optimizer to reason about them correctly to be worth having.
- **Sharding, columnar storage, vectorized execution**: multi-year even for funded teams with existing engines as precedent — Postgres's own columnar/vectorized story is still largely extension-based (Citus, `pg_columnar`) for exactly this reason. Named here as honest long-term context, not a plan.

## What was deliberately not carried over from the DeepSeek plan, and why

- **Team structure (Technical Lead, Storage Lead, SQL Lead, ...) and the $842K annual budget.** These describe a staffed effort. Repeating them here would misrepresent how this project is actually being built (one developer plus AI-assisted implementation) and wouldn't help track anything real.
- **Month-numbered milestones (M1 through M9, Month 2 through Month 20).** Without a team of the assumed size, these dates aren't load-bearing — keeping them would just create a roadmap that's wrong on day one.
- **Claims of current completion that didn't match the repo** (e.g., "10,000+ lines," "MVCC" listed as done pre-Week-2, WAL described as working before its recovery path was actually fixed). `PROGRESS.md` is the source of truth for what's actually built and tested; this plan doesn't restate unverified claims.
- **GitHub-stars/fork-count/contributor targets and a release-channel/deployment strategy** (Snapshot/Alpha/Beta/Stable channels, Docker/Kubernetes/cloud deployment options). These are real concerns for a project actively courting outside users and contributors; they're not useful to plan against before Part 1 is even finished, and can be revisited once there's something for a wider audience to actually run.

## Testing strategy (kept, because it's good practice regardless of team size)

- Storage engine, buffer pool, WAL: tested against real crash/restart scenarios, not just happy-path unit tests (established in Week 1 — see `CrashRecoveryTest`).
- Transactions/MVCC: tested with real concurrent transactions and a real induced deadlock, not mocked concurrency (established in Week 2).
- Indexing: tested at a scale that actually forces the interesting code paths (multi-level splits), not just a handful of keys (established in Week 3's B+Tree work).
- Networking/auth/TLS: tested over real sockets and, for TLS, a real certificate generated with the JDK's own `keytool` — not a mocked `SSLContext` (established in Week 4).
- The standard to hold every future addition to: **if a claim of correctness isn't backed by a test that was actually run, it isn't verified yet.**

What the same standard will actually require for Part 2's higher-risk items, named now rather than discovered later:
- **Vacuum**: needs a test that proves dead space is genuinely reclaimed (table size stops growing under a sustained update workload) *and* that visibility is preserved for any transaction with an older snapshot still open — getting the second part wrong is a correctness bug, not a performance one.
- **Cost-based optimizer**: needs tests that don't just check the final answer is right (a rule-based planner already gets that right) but that the *chosen plan* is the cheaper one under a known data distribution — otherwise a regression that silently reverts to always-seq-scan would pass every existing correctness test.
- **Replication**: needs real fault injection — kill the follower mid-stream, kill the leader mid-write, verify the follower catches up correctly rather than just testing the happy path where nothing ever fails.
- **PostgreSQL wire protocol compatibility**: ✅ done this way — verified against `psql` (the real reference client) and `psycopg2` (an independent driver implementation), not a custom test harness that only exercises what StratosDB's own code expects to receive.
